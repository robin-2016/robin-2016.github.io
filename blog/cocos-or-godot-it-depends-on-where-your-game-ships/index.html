Cocos 还是 Godot？先看你的游戏发在哪

同样免费，只有一个官方支持导出绿泡泡小游戏。

摘要

Cocos Creator 擅长小游戏和移动端，Godot 擅长独立游戏和跨平台。两者没有绝对的强弱，选哪个取决于游戏最终发在哪里。本文基于 2026 年 10 月的最新版本，逐项对比优势、缺点和适用场景。

先说结论

  • 目标平台是绿泡泡小游戏、抖某音小游戏等国内小游戏平台，选 Cocos Creator。
  • 目标平台是 Steam、PC 等桌面端的独立游戏，选 Godot。
  • 想写 C#，倾向 Godot；想做网页和小游戏，倾向 Cocos。
  • 如果你的游戏要同时上小游戏和 Steam，两边都有取舍，后面有专门一节。

先看版本和现状

资料检索于 2026 年 10 月 20 日，数据来自 GitHub 和官方文档。

项目 Cocos Godot
当前稳定版 Cocos Creator 3.8.8（2025 年 12 月 16 日） Godot 4.7.2（2026 年 8 月 18 日）
协议 引擎代码 MIT；3.x 编辑器免费但闭源，另有官方使用条款 MIT，无分成、无席位费
GitHub 星数 约 9,900（cocos-engine） 约 11.9 万
主要语言 TypeScript / JavaScript GDScript，另支持 C# 和 C++
在做的新东西 COCOS 4，目前仍是 alpha（最新 4.0.0-alpha.35，2026 年 10 月 13 日） 4.8 开发中

有一个容易被忽略的变化：Cocos 官方在 2026 年 1 月宣布了 COCOS 4，把引擎和编辑器拆开，编辑器部分的方向叫 PinK，并改用标准 MIT 协议。但它到现在还是 alpha，官方公告也说小游戏平台支持会逐步到来。所以今天要做正式项目，用的仍然是 Cocos Creator 3.8.x。

Cocos Creator：优势

1. 小游戏是主场。 官方支持的发布目标包括 Web、iOS、Android、Windows、Mac、鸿蒙，以及绿泡泡、抖某音、OPPO、华为快游戏、vivo、荣耀等小游戏平台。Web 和小游戏上运行的是纯 JS 运行时，原生平台底层则是 C++。

2. 前端开发者几乎零门槛。 脚本用 TypeScript 或 JavaScript，两者可以混用。组件写法大致是这样：

import { _decorator, Component } from 'cc';
const { ccclass, property } = _decorator;

@ccclass('Player')
export class Player extends Component {
    @property
    speed = 200;          // 会显示在属性检查器里

    update(dt: number) {
        // 每帧调用
    }
}

3. 2D 工具链完整。 内置 UI 系统、带曲线编辑的动画系统，并支持 Spine、DragonBones、TiledMap 和 Box2D。手机扫码就能预览。

4. 在包体上下了功夫。 3.8.5 起 WASM 模块延迟加载，Spine 模块体积比 3.8.4 缩小约 40%。小游戏有包体上限，这类优化会直接影响能否过审。

Cocos Creator：缺点

1. 编辑器平台少。 官方手册只写了编辑器支持 Windows 和 Mac，没有提 Linux。

2. 小游戏也有硬限制。 绿泡泡小游戏手册写明主包不能超过 4MB（含全部代码和资源），超出的资源要走网络下载，而且脚本文件不能远程下载。VideoPlayer 和 WebView 不支持。使用绿泡泡引擎插件的“分离引擎”模式时，目前只支持 JS 模式，不能用 Wasm 物理。

3. 版本处于过渡期。 3.8.8 发布于 2025 年 12 月，此后 GitHub 上没有新的 3.8.x 正式版，而新版 COCOS 4 还是 alpha。选 3.8.x 是稳定但迭代放缓，选 COCOS 4 则要接受 alpha 阶段的不确定。

4. 社区体量差距明显。 引擎仓库星数约 9,900，Godot 约 11.9 万，找国际社区的现成方案会更吃力。

Godot：优势

1. 完全开源，没有任何附加条款。 MIT 协议，没有分成，没有席位费，由 Godot Foundation 和赞助商维护。

2. 节点和场景架构，上手快。 GDScript 语法接近 Python，也能用 C# 和 C++（GDExtension）。一个最小的移动脚本：

extends CharacterBody2D

@export var speed := 200.0

func _physics_process(_delta):
    velocity = Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down") * speed
    move_and_slide()

3. 2D 和 3D 都在持续进步。 4.6 起 Jolt 成为新项目的 3D 默认物理引擎。4.7（2026 年 6 月发布）新增矩形面光 AreaLight3D、HDR 输出、2D 编辑器的 Scene Paint 模式，Android 上的编辑器环境 GABE 也已稳定，可以直接在安卓设备上导出游戏。

4. 独立游戏的实战案例多。 Brotato、Buckshot Roulette、Dome Keeper、Cassette Beasts 都是 Godot 做的。

Godot：缺点

1. 没有官方的国内小游戏导出。 想上小游戏只能从 Web（HTML5）导出入手。社区里有人手工移植到绿泡泡小游戏，但要改引擎的 JS 层、音频、文件系统和 PCK 分包，而且我找到的案例用的是 Godot 3.6，没有找到 2026 年的现成方案。

2. Web 导出限制不少。 按官方文档：

  • Godot 4 的 C# 项目目前无法导出到 Web；
  • Web 只能用 Compatibility 渲染器（WebGL 2.0），WebGPU 暂不支持；
  • 4.3 起默认单线程导出，要开多线程得配置跨域隔离头；
  • 默认的音频采样播放模式没有混响等音效；
  • Safari 的 WebGL 2.0 有已知问题。

官方文档没有给出体积数字，只说 .wasm 用 gzip 能压到约四分之一，建议用 Brotli 并精简导出模板。

3. 主机平台靠第三方。 官方直接支持的只有 Steam Deck（走 Linux 模板），Switch、PS5、Xbox 要找 W4 Games 这样的第三方移植商。

4. 国内平台的官方适配少。 国内小游戏之外，鸿蒙也没有 Godot 官方支持，目前只看到社区分支在做鸿蒙导出，而 Cocos 官方在直接适配。

把两者摆在一起

维度 Cocos Creator 3.8 Godot 4.7
国内小游戏 官方支持，主包 4MB 上限 无官方支持，需手工移植
Web / H5 纯 JS 运行时 WebAssembly，限制较多
脚本语言 TypeScript / JavaScript GDScript，另有 C# 和 C++
桌面 / Steam 官方支持 Windows 和 Mac 成熟，案例多
主机 官方资料未覆盖 官方只有 Steam Deck，其余靠第三方
鸿蒙 官方适配 无官方支持，只有社区分支
3D 有 PBR 和延迟管线 持续迭代，Jolt、面光源、HDR
协议 引擎 MIT，3.x 编辑器另有条款 MIT

3D 这一栏我没有写“谁更强”：检索中没有找到 Cocos 3.8 和 Godot 4 的权威对比，只有一些二手轶事，不足以下结论。

如果游戏要同时上小游戏和 Steam

这是最纠结的情况，两条路各有成本：

  • 选 Cocos：小游戏最顺，桌面版也能出，但 Steam 方向我没有查到足够的资料，建议先做个小原型验证。
  • 选 Godot：Steam 和 PC 顺，小游戏版要自己啃 Web 导出和 4MB 包体，一旦用了 C# 就完全走不了 Web。

比较务实的做法是：先确定最重要的那一个平台，用它决定引擎，另一个平台作为“能做到更好”的补充。

三行速记

  • 发国内小游戏：Cocos Creator 3.8.8，注意 4MB 主包和脚本不能远程加载。
  • 做独立游戏上 Steam：Godot 4.7.2，想上 Web 就别用 C#。
  • COCOS 4 还是 alpha，正式项目先用 3.8.x。
